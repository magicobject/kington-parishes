# Standing instructions for this repo

These apply to every change here, not just when explicitly asked for.

## Before any push to origin
- Run `npm test` (Playwright suite) and `npm run audit` (`npm audit --audit-level=high`). Fix real findings — don't suppress, downgrade, or skip them to get a push out.
- If the change touches page content, structure, or CSS, make sure `test/accessibility.spec.ts` is included in that run and still passes with zero violations.
- Whenever the whole suite (`npm test`) is run, report the number of tests run and the time taken, prefixed with this repo's name (e.g. "kington-parishes: 121 tests passed in 15.2s") — the count and duration are in Playwright's own summary line, the name prefix makes it scannable when work spans multiple sites in one session — a quick way to notice a regression in either coverage or speed, in the right project.

## Accessibility
- Every page must pass an axe-core scan (`@axe-core/playwright`, via `test/accessibility.spec.ts`) with zero violations. New pages need an entry in `test/support/pages.ts` — the accessibility spec picks them up automatically from there.
- This site uses a reveal-on-scroll animation (`.reveal` / `.in`). A scan run right after `page.goto()` will false-positive on below-the-fold elements still at `opacity:0`. If you touch the accessibility spec, keep the settle step that force-adds `.in` and kills the transition/opacity/transform inline before scanning — toggling the class alone isn't enough.
- Any new heading needs to fit the existing outline (no skipped levels — h1 → h2 → h3, not h1 → h3).
- Any new text/background color pairing must clear WCAG AA contrast (4.5:1 for normal text, 3:1 for large text/UI components) — compute it (relative luminance), don't eyeball it.
- Every `<iframe>` needs a `title`; `aria-label` only belongs on elements with an ARIA role, never a bare `<div>`.

## Security
- Keep `npm run audit` clean (no unresolved high/critical) before any push.
- Don't add third-party scripts, trackers, or embeds (iframes included) without adding whatever they need to `public/_headers`' CSP first — and actually verifying it. `npm run serve` does NOT apply `_headers` (it's a Cloudflare-only convention), so a CSP gap won't show up there; it shipped silently once already (a Google Maps embed with no `frame-src`, rendering as "This content is blocked" in production). Verify with `npx wrangler dev`, which serves `public/` through the real asset handler, `_headers` included — check the browser console for CSP violations after any change to `_headers` or to what a page loads/embeds.

## Multi-developer workflow
This repo now has more than one person making changes through Claude Code. `users.json` (repo root) is the roster — each entry has `firstName`, `lastName` and `github` (their GitHub account name). These checks only run inside Claude's own workflow; they don't stop anyone with direct repo access, but they do keep an honest record of who did what, and give a hook to later restrict what a given user can do.

- **Before starting work on any change**, run `git pull origin main` — someone else may have pushed since this session last looked.
- **Before pushing any change back to origin**, run `git pull origin main` again, to catch anything pushed while the change was in progress.
- **When adding a changelog entry** (see "Build numbers" below), identify the author automatically rather than asking: run `gh api user --jq .login` to get the current GitHub account, look it up in `users.json`, and use that person's `firstName` + `lastName` as the `changelog-author`. If the logged-in account isn't in `users.json`, stop and ask — add them to the roster first rather than guessing or leaving attribution blank.
- Work in a git worktree when another session may be editing this repo; the commit hook refuses to build from unstaged changes.

## Build pipeline
- `public/*.html` is generated from `templates/*.html` + `src/pages/*.html` + `src/pages.config.mjs` + `src/site.config.mjs` by `scripts/build.mjs` — never hand-edit it, edit the source and run `npm run build`.
- `public/css/style.css` is the one thing in `public/` that's hand-maintained, not generated.
- `public/js/calendar-events.js` is also generated (from `src/events.config.mjs`) — see "Calendar & events" below.
- The pre-commit hook bumps the build number and regenerates `public/` automatically on every commit — never do either by hand.
- **Never hand-write a `?v=` on a `<link>`/`<script>`.** `versionAssetUrls` in `scripts/build.mjs` appends `?v=<content hash>` to every same-origin `href`/`src` on those tags, and fails the build if the file doesn't exist. The build number deliberately appears only on `/updates.html` (not in footers, not in cache-busters, and there's no sitemap `<lastmod>`), so a commit only changes the generated pages it actually affects — keep it that way rather than stamping anything per-build into every page.
- **Pages with a Leaflet map use the `{{LEAFLET}}` token** (`templates/leaflet.html`) for Leaflet's own CSS/JS, followed by their own map script.

## Home page journey line ({{JOURNEY_NAV}})
The home page's "Jump to a church" nav (`index.html`, `nav.ridge-nav`) is `{{JOURNEY_NAV}}`, which `renderJourneyNavToken` in `scripts/build.mjs` expands (via `scripts/ridge.mjs`) into an SVG: a schematic elevation profile of the ride Kington → Huntington → Old Radnor → Kinnerton → Titley, each church's sketch (`public/img/journey/<slug>.png`, cut from `public/img/five-churches.gif`) standing on it, with its name, as a link to that church's section of `our-churches.html`. Never paste the SVG into the page — use the token. Other pages' headers have no line (removed 12 Oct 2026 to save screen space).
- Church positions come from `src/churches.config.mjs`; the order and sketch sizes (and optional `lift`, which raises a sketch so the line doesn't cut through it) from `src/journey.config.mjs`; the ground heights from `src/journey-profile.json`, which is **generated** by `npm run journey:profile` (EU-DEM 25 m via OpenTopoData, ~150 m spacing along the straight line between churches; needs the network, so it isn't part of the build). If you move a church's `lat`/`lng` or change the journey order, re-run it — the build refuses a stale profile.
- It is schematic, not a survey: ground higher than the tallest church is compressed to a quarter of its excess (`compressHeights`), because the straight line crosses ridges (394 m between Huntington and Old Radnor) that would otherwise flatten every church into the valley floor.
- Sketch colour is cream (`#F2E6C4`) on the hero's dark gradient; labels use `.ridge-label`. Each church is a link with a text name, so keep the labels.

## Calendar & events
`src/events.config.mjs` (`ONE_OFF_EVENTS`, `RECURRING_SERIES`) is the single source of truth for the parish calendar — edit the arrays there, then `npm run build`. Three things come from it:
- `public/js/calendar-events.js` — generated (pre-expanded, flat, sorted) for the interactive calendar (`calendar.js`). Don't hand-edit this file; it's overwritten on every build, same as `public/*.html`.
- `calendar.html`'s `<noscript>` fallback list, via the `{{EVENTS_NOSCRIPT}}` token — one-off events only, same scope the list always had (recurring series don't belong in it).
- `calendar.html`'s `Event` structured data (one schema.org `Event` per concrete occurrence, per Google's own guidance — not one Event plus a recurrence rule), filtered to events on or after the build date so a stale rebuild doesn't keep listing events that already happened. `placeFor()` in the same file maps an event's free-text `location` to a `Place` with a real address when it matches one of the five churches, and to a bare-name `Place` otherwise (never guess an address for an unrecognised venue).

- **Adding a noticeboard poster ("What's coming up" on `index.html`, `#noticeboard`) also means adding it to the calendar — do this automatically, without being asked.** When a `.noticeboard-card` is added for a *dated, one-off* event (it'll usually carry a `data-expires` attribute and a specific date/time in its `.date` line or poster `alt` text), add a matching entry to `ONE_OFF_EVENTS` — same date, time, title and location, inferred from the card's `.date` line and poster `alt` text — then `npm run build`. Skip this for posters with no specific date/time (an ongoing notice like the Zero Waste Food Project poster, or an announcement like the St Stephen's heritage grant) and for recurring groups already covered by a `RECURRING_SERIES` entry (Stay & Play, Marches Voices, Kington Zero Waste) — adding those to `ONE_OFF_EVENTS` too would double them up on the calendar. Check `ONE_OFF_EVENTS` first in case the event's already there (e.g. from a phone/email request before the poster existed) — don't create a duplicate.

## Site search
The header search box (`templates/header.html`, `public/js/search-ui.js`, `public/js/search-match.js`) is driven by `public/search-index.json`, which `scripts/build.mjs` regenerates from scratch on every build via `scripts/build-search-index.mjs` — never hand-edit that JSON file.

- **Every `h1`/`h2`/`h3` on a searchable page gets an anchor id, automatically.** `ensureSectionIds` walks each page's rendered HTML at build time and injects an `id="…"` (slugified from the heading's own text) onto any heading that doesn't already have one and isn't already inside an id'd wrapper (an `<article id="…">`, a `<section id="…">`, etc.). If a heading you're editing unexpectedly gains an `id` attribute after a build, this is why — it's not a mistake, it's what makes that heading a stable, deep-linkable search result. Give a section its own explicit `id` if you need control over the exact slug; otherwise leave it to the build.
- **`/updates.html` and `/404.html` are never indexed at all** (`isIndexable`) — the changelog is deliberately unlisted/noindex build-log content with no real content to surface, either way.
- **The hidden `/help`/`/help-*` guide has its own search scope.** Its entries ARE in `search-index.json` (tagged `scope: "help"` by `scripts/build.mjs`, via `isHelpPage`), but `public/js/search-ui.js` only surfaces them while the visitor is already on a help page — and while there, hides every *ordinary* result, so the search box only ever returns one or the other, never a mix. This keeps the guide fully searchable for the website team without an ordinary site visitor being able to search their way into internal process documentation from a normal page. `isSearchablePage` (excludes both the never-indexed pages above and the help guide) is the predicate for "public scope" — it still gates the sitemap, unchanged.
- **Page titles in `pages.config.mjs` are authored pre-escaped for HTML interpolation** (e.g. `'Services &amp; Events — Kington Parishes'`). The indexer decodes that back to a plain `&` before it goes in the JSON — the search dropdown is plain text, not HTML, so it must never end up displaying a literal `&amp;`.
- **All of this is unit-tested without a browser**: `scripts/build-search-index.mjs`'s indexing logic and `public/js/search-match.js`'s ranking logic are both pure functions, covered by `test-unit/*.test.mjs` (`npm run test:unit`, Node's built-in test runner — fast, no Playwright needed). The end-to-end UI behaviour (typing, keyboard nav, navigation, the updates.html exclusion, the help guide's separate scope) is covered separately in `test/search.spec.ts`.

## Church portal pages and the {{PEOPLE:...}} token
Each church has its own portal page (`church-kington.html`, `church-titley.html`, `church-old-radnor.html`, `church-kinnerton.html`, `church-huntington.html`), reachable from `our-churches.html` two ways: a "More about ... →" text link in that church's `.links-row`, and the church's own photo (`.parish-photo`), both pointing at the same URL. Not in the primary nav — reachable only from `our-churches.html`, same pattern as Donate/Parish News Archive. The photo link carries an `aria-label` ("More about ...") rather than relying on the `<img>`'s own `alt` (a scenic description, not a link purpose) as its accessible name — keep both in sync if you change either.

- **Clergy and church officers are DRY, via `src/people.config.mjs`.** `CLERGY` (serving all five churches) and `CHURCH_OFFICERS` (keyed by church slug — `kington`, `titley`, `old-radnor`, `kinnerton`, `huntington`, all populated) are the single source of truth for every person card. A page's source writes `{{PEOPLE:clergy}}` or `{{PEOPLE:<church-slug>}}` where the card grid should go; `scripts/build.mjs`'s `renderPeopleTokens` expands it into real `<div class="card">` markup. Add, remove, or edit someone once in `people.config.mjs` and every page that lists them (`our-people.html`, which shows every church, and that church's own portal page) picks it up — that's the whole point: don't hand-edit person cards directly into a page's HTML.
- **A person serving two roles at the same church gets one card, not two** — join the roles with `·` in `role` (e.g. `'Churchwarden · Organist'`), same as Greg Wright's `'Churchwarden · Interim Treasurer'`. A person serving *different* churches (Ruth Jones, Nicola Cavell) gets a separate entry under each church's key in `CHURCH_OFFICERS` — same name, same `contactLink(email)` if they have one, but each is its own card since it's tied to that church's section on `our-people.html`/that church's portal page.
- **A person's email is optional** — pass it to the `contactLink(email)` helper at the end of their `bio` string (`bio: '...' + contactLink('someone@example.com')`); it renders an obfuscated `{{OBFUSCATE_MAILTO:...}}` "Get in touch →" link, or nothing at all if you pass `undefined`/omit it. Never hand-write a mailto or paste a plain email into `bio` — that bypasses obfuscation.
- **`renderPeopleTokens` runs before `ensureSectionIds`/search indexing**, not after — so each expanded person's `<h3>` is a real heading by the time anchor ids get injected and the page gets indexed for search, not a token search can't see. If you add a new `{{...}}`-style token to the pipeline, it needs to expand before that point too, for the same reason.
- **The church descriptive content itself (photo, body text, facts, links) is NOT DRY** — each portal page currently duplicates its church's section from `our-churches.html` by hand. See the note below.

The hooks enforce this (`docs/hooks.md`); do not do it by hand. ## Data kept in sync by hand
Nothing here is generated from the other — each pair below is two separate places that happen to describe the same thing, so editing one without the other goes stale silently.

- **Each church's location is DRY; its descriptive content isn't.** `src/churches.config.mjs` (`CHURCHES`) is the single source for each church's name, locality, lat/lng, what3words and `sameAs` links. The build generates everything that needs those from it: the `Church` entries in the `our-churches` JSON-LD `@graph` (`churchStructuredData` in `src/pages.config.mjs`), the homepage's five-pin map (`{{CHURCHES_MAP}}` in `index.html`, whose pins `public/js/churches-map.js` reads from a `data-churches` attribute), each portal page's single-pin map (`{{CHURCH_MAP:<slug>}}`), and the calendar's Event `location` localities (`placeFor` in `src/events.config.mjs`). Moving a pin means editing `lat`/`lng` there, once — never hardcode coordinates into a page or map script. Still hand-maintained, though: the visible `links-row` on `our-churches.html` (Wikipedia/National Churches Trust/what3words links), and each church's photo/body text/facts/links duplicated from `our-churches.html` onto its own `church-<slug>.html` (including the what3words links in that prose). Adding, removing, or editing a church still means updating those by hand, alongside its `CHURCHES` entry. (The People cards are DRY too — see "Church portal pages" above.)
- **what3words → coordinates isn't something Claude can resolve on its own.** The `https://what3words.com/word.word.word` link needs no API. Converting that address to a lat/long for `CHURCHES` in `src/churches.config.mjs` needs either the what3words API (needs a key we don't have) or the actual coordinates, read off the map by a human — don't spend time trying to scrape/reverse-engineer what3words.com for this, it's been tried and their site blocks it.
- **`SITE_URL` in `scripts/build.mjs`** is the one constant canonical links, Open Graph tags, and every JSON-LD URL all key off — now the real domain (`https://www.kingtonparishes.org.uk`), live since 6 September 2026. If this ever needs to move again (a new domain), update it here.
- **Newsletter signup confirmation copy.** Double opt-in is currently switched **off** in MailerLite (the sending domain isn't verified for it yet — see the vicar/whoever manages MailerLite before re-enabling), so a successful signup is immediate: no confirmation email gets sent. Four places currently say so explicitly and would all need to change back together if double opt-in is re-enabled: `src/worker/subscribe.mjs`'s `SUCCESS_MESSAGE` (the only one that actually matters for what a visitor sees — `public/js/newsletter-signup.js` displays this value directly, it's not hardcoded in the page), `src/pages/newsletter.html`'s intro paragraph above the signup form, and `src/pages/privacy-policy.html`'s "Why we collect it" section.
