    Under the hood

    The rest of this guide deliberately stays non-technical. This page doesn't — it's for anyone who wants to understand exactly what this site runs on: hosting and DNS, how it's built from templates, what gets tested before a change goes live, the newsletter, and how the small amount of server-side code is secured.

    Hosting

    A Cloudflare Worker, not just static hosting

    The live site is a Cloudflare Worker. Its configuration (wrangler.jsonc) points Cloudflare's asset handler at public/, the folder the build script generates — so almost every request is served as a plain static file, exactly like conventional web hosting. The one addition is a small JSON API endpoint, /api/subscribe, that the newsletter signup form talks to — see Newsletter below.

    Deployment is automatic: Cloudflare's GitHub integration watches the main branch, and every push triggers a fresh build and deploy — no separate deploy step to run by hand, and typically live in well under a minute. This is the mechanism behind step 5 in Making a change ("the live site rebuilds itself").

    DNS

    Also managed in Cloudflare

    The kingtonparishes.org.uk domain's DNS lives in the same Cloudflare account as the Worker, with the domain attached to the Worker as a custom domain. That's a deliberate, common pairing — Cloudflare can issue and renew the site's TLS certificate and route traffic straight to the Worker without a separate DNS provider in the loop. It replaced the previous host (Squarespace) at go-live on 6 September 2026; see /updates for that migration's own build-log entries, and DNS setup for a closer look at the domain's actual records.

    Build & templates

    Built from templates, not hand-copied HTML

    No page's HTML is written out in full anywhere. Each one is assembled at build time (scripts/build.mjs) from four pieces: templates/*.html (the shared header, footer, safeguard banner and page shell), src/pages/*.html (just that page's own content — no <head>, no nav, no footer), src/pages.config.mjs (the nav, each page's title and meta description), and src/site.config.mjs (facts repeated across the site — phone number, email, the donate link — each substituted wherever a matching placeholder appears in a page's content).

    This is what keeps the site DRY ("Don't Repeat Yourself"): a fact like the parish office's phone number, or a person's role and contact details, is typed in exactly one place, and every page that shows it — however many there are — picks it up automatically the next time the site is built. Change the phone number in site.config.mjs once, and it updates on every page that shows it; add a churchwarden to src/people.config.mjs once, and their card appears on both Our People and their own church's page. Without this, the same fact would need finding and editing by hand on every page that happened to mention it — easy to do consistently once, easy to let quietly drift out of sync after the tenth edit.

    Not every file in public/ is generated, though — a handful (the stylesheet, the JavaScript, the images, robots.txt, _headers) are the real, hand-maintained originals, sitting directly in the folder Cloudflare serves, because there's no per-page fact to template: a stylesheet doesn't repeat page to page, it defines how every page looks. Everything else under public/ — every *.html file — is a generated build artefact: editing one directly would have no lasting effect, since it gets silently regenerated (and any hand-edit overwritten) the next time anyone builds the site, which happens automatically on every commit via a git hook. Claude already knows this file-by-file — it edits the real source under src/, templates/, or the genuinely hand-maintained files in public/, and never a generated page directly.

    Testing

    What gets checked before anything reaches the live site

    Every change runs through the same automated suite before Claude pushes it — this project's standing rule is that nothing goes live untested. Four things it checks:

    Reactive — works well on any device

    Playwright tests real layouts at both desktop and handheld (mobile) viewport widths — the primary nav's collapsed menu toggle below 860px, the calendar's day grid never forcing the page to scroll sideways, and more — not just an assumption that the CSS behaves as intended.

    WCAG AA accessible

    Every single page is scanned with axe-core, with zero violations tolerated: colour contrast, heading order, form labels, ARIA usage and more, checked automatically rather than eyeballed.

    Functionally correct, no regressions

    Several hundred Playwright tests exercise real behaviour across the whole site — navigation, forms, the calendar, search, the footer's build number, each page's own title and canonical link — so a change made for one page can't silently break another without the suite catching it.

    Secure

    npm audit blocks any push carrying a known high or critical severity dependency vulnerability (see MailerLite API security below), and the same test suite acts as a regression net for the security headers whenever public/_headers changes.

    All of it runs locally in well under a minute, and its result — pass or fail — is what actually decides whether a change gets pushed, not a judgement call. See step 3 of Making a change.

    Multiple contributors

    Who changed what: users.json

    More than one person now makes changes to this site through Claude Code. users.json, at the root of the repository, is the roster: each entry is a first name, last name and GitHub account name. It's what lets every change be attributed to the person who actually made it, rather than a single generic "the website team".

    Before adding an entry to the /updates changelog, Claude looks up the GitHub account currently signed in (gh api user) against users.json, and credits that person by name — that's the changelog-author shown next to each build number. If the signed-in account isn't on the roster, Claude asks for it to be added rather than guessing.

    This is a check Claude runs, not a security boundary — it doesn't stop anyone with direct repository access from doing anything, but it does keep an honest, automatic record of who did what, and gives a foundation to later limit what a given contributor is allowed to change.

    Newsletter

    InSpire Newsletter signups, via MailerLite

    The InSpire Newsletter signup form doesn't talk to MailerLite directly from the browser. Instead:

    1. The form posts to the Worker

    A visitor's email (and optional name) is sent to this site's own /api/subscribe endpoint — never straight to a third party.

    2. The Worker calls MailerLite

    Server-side code (src/worker/subscribe.mjs) validates the address, then calls MailerLite's API to add it to the "InSpire Newsletter" group.

    3. Immediate subscription

    Double opt-in is currently switched off in MailerLite (the sending domain isn't yet verified for it), so a successful signup is immediate — no confirmation email is sent. See CLAUDE.md for where this reverts if that changes.

    MailerLite API security

    How the MailerLite API endpoint is secured

    The MailerLite key is a Cloudflare secret

    It's never committed to GitHub and never appears in this repository — only the non-secret group id lives in wrangler.jsonc. On a failure, only MailerLite's own error status is logged server-side; the key and the raw request are never written to a log.

    Server-side validation

    Email format and length, and name length, are checked before anything reaches MailerLite — the API is never handed unvalidated input.

    A honeypot field

    A hidden form field real visitors never see, but generic bots filling in every field will. A filled honeypot is answered with a normal success response rather than an error, so bots don't learn to detect and route around it.

    Security response headers

    Every response carries a Content-Security-Policy, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, a restrictive Permissions-Policy, and HSTS (public/_headers) — defence in depth against injected scripts, clickjacking and downgraded connections, on every page, not just the API.

    Dependency scanning on every push

    A git hook runs npm audit --audit-level=high before any push can complete, blocking it outright if a dependency carries a known high or critical severity vulnerability.

    A published disclosure contact

    An RFC 9116 security.txt points anyone who finds a real vulnerability at a monitored contact address, rather than leaving them no way to report one responsibly. Remember to update security.txt annually — its Expires date has to stay within a year or it's treated as lapsed; just ask Claude to renew it.

    The code

    Where it all lives

    Every piece of this — page content, templates, the build script, the styling, and the Worker code behind the newsletter API — lives in one public GitHub repository: github.com/magicobject/kington-parishes. Every commit that reaches main is tagged with its own build number (e.g. build-2026.09.08.005), so any past version of the site can be checked out by name — see /updates for the human-readable version of that same history.

    Build, test and deploy: where each happens

    No CI on GitHub — the build and the test suite both run locally

    It's easy to assume a project like this has a GitHub Actions workflow that builds and tests every push. It doesn't — there's no .github/workflows directory in the repository at all, just Dependabot's config for dependency update PRs. GitHub's only job here is to host the repository and be the place Cloudflare watches for new commits on main.

    The actual building and testing happens on whichever machine is making the change — see Build & templates and Testing above. npm run build regenerates public/ on every commit (via the pre-commit git hook), and npm test plus npm run audit run before every push, both locally, both before anything reaches GitHub at all. By the time a commit lands on main, it's already been built and already passed the full test suite — nothing on GitHub's side builds or tests it again.

    What a push to main does trigger is Cloudflare's own deployment, via its GitHub integration (see Hosting above) — but that's a deploy, not a build or test step: it uploads the already-built public/ folder and the Worker code exactly as they were committed, live in well under a minute. If a change were ever pushed without running the local build and test suite first, Cloudflare would deploy it anyway, untested — which is exactly why that suite running locally, before every push, is a standing rule for this project rather than a courtesy.
